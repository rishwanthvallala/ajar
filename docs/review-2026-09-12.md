# Project review — 12 September 2026

Reviewed checkout: `0b21300`. This is an end-to-end source and local validation review, not a certification that every path is correct. No production code was changed, and no production service was modified or attacked.

The architecture has clear ownership boundaries, but several implementations break those boundaries during disconnects, concurrent saves, and error handling. The highest priorities are the encrypted protocol's direction ambiguity, actual enforcement of guest revocation and sandbox restrictions, and preventing stale editor/runtime copies from overwriting durable files.

**What the project is**

There are two applications sharing one relay process:

| Component | Responsibility and source of truth |
|---|---|
| `crates/ajar-proto` | Nine-byte frame header, JSON control types, binary PTY/document streams, AES-GCM encryption. The TypeScript clients and smoke harness implement this format separately. |
| `crates/ajar` | Owns a real workspace, local PTYs, live Yrs documents, checkpoint, credential warnings, sandbox policy, process limits, and host controls. Disk is authoritative for external changes; live documents supply debounced editor writes. |
| `crates/ajar-relay` hosted sessions | In-memory host/guest membership, routing, locks, reconnect grace, bounded outgoing queues, and optional encrypted workspace snapshots. |
| `web` | Guest connection, terminal rendering/replay, virtualized tree, lazy Monaco editor, Yjs binding, presence, and offline snapshot reading. |
| `pad` | Each tab has Monaco/Yjs documents and its own Wasmer/WASIX filesystem and shell. Python and a limited Unix tool set run in the visitor's browser. |
| Relay pad store | Plaintext JSON files on disk, sequence numbers, whole-file last-write-wins updates, per-pad limits, seven-day expiry, permanent name tombstones. This is separate from encrypted hosted-session snapshots. |
| Deployment | Caddy serves two origins, proxies HTTP/WebSockets, adds isolation/security headers, and serves mirrored WASM packages. systemd manages the relay. GitHub Actions checks the agent stack and publishes agent binaries. Docker is another advertised relay packaging path. |

The machine-sharing startup sequence is: validate and scan a folder; prepare sandbox, limits, checkpoint and warnings; generate session ID/key; connect the host to the relay; print/display the link; accept guests. Guests request terminals/files/documents through the relay. PTY threads feed the agent, which encrypts output. The watcher reconciles external file changes, coalesces tree updates, and schedules snapshots. Shutdown should flush documents and explicitly close the relay session.

The pad sequence is: derive or mint a name; GET durable files; join a peer session; initialize editor models; obtain or seed live document state; lazily start WASIX. Typing broadcasts Yjs updates and schedules HTTP saves. Commands change a local filesystem, which is diffed and published after completion. Other browsers receive a nudge and reread the store. These three representations—document, editor model, runtime filesystem—are where most data-loss defects concentrate.

**Priority definitions**

P1: fix before depending on the affected security or data-safety guarantee. P2: important correctness, availability, or verification gap. “Reproduced” means executed locally; “source trace” means a concrete path established from the code, with platform-dependent behavior explicitly identified.

**R01 — P1: encrypted frames do not authenticate their direction. Reproduced at the crypto layer.**

[Frame header authentication](D:/ajar/ajar/crates/ajar-proto/src/lib.rs:90), [browser authentication](D:/ajar/ajar/web/src/sealed.ts:108), [PTY input handler](D:/ajar/ajar/crates/ajar/src/main.rs:621).

Host-to-guest output addressed to participant 2 and guest-2-to-host input both use the same key and header `(PTY, terminal_id, 2)`. The host's targeted terminal replay is therefore a valid ciphertext in the reverse direction. A relay can reflect it unchanged; no key or forged GCM tag is needed. Outgoing nonces are not registered as incoming nonces, so the duplicate cache does not stop the first reflection. The host then interprets the decrypted terminal output as terminal input. Command-looking output can consequently be submitted to the shell.

The local reproduction proves that a targeted output ciphertext opens in the reverse context using the actual browser Sealer. The equivalent Rust seal/open and PTY dispatch paths were traced; an actual malicious-relay shell execution was not run. Authenticate an explicit direction and message purpose, or derive separate keys for each direction; reject reflected frames before dispatch. Add a cross-direction protocol regression, not just encrypt/decrypt round trips.

**R02 — P1: Linux write confinement omits truncation. Source trace plus primary platform documentation.**

[Linux ruleset](D:/ajar/ajar/crates/ajar/src/sandbox.rs:474).

The launcher builds filesystem rights from `ABI::V1`, even on newer kernels. That omits the separate truncation right introduced in ABI 3. A guest can invoke truncation on an otherwise user-writable file outside the allowed workspace, even though ordinary write-open tests are denied. This contradicts the advertised write boundary. The kernel explicitly documents that truncation does not require `WRITE_FILE`; `truncate(2)` and read-only opens with `O_TRUNC` are relevant cases. [Linux Landlock documentation](https://docs.kernel.org/userspace-api/landlock.html#truncating-files).

Negotiate and handle the necessary access rights, and refuse or accurately downgrade confinement on kernels that cannot enforce them. Add a real truncation test against a fixture outside the workspace. No kernel-level escape was executed on this Windows machine.

**R03 — P1: a guest without the content key can crash the host with a control frame. Source trace.**

[Guest forwarding](D:/ajar/ajar/crates/ajar-relay/src/ws.rs:234), [control parsing](D:/ajar/ajar/crates/ajar/src/main.rs:546), [error propagation out of the event loop](D:/ajar/ajar/crates/ajar/src/main.rs:407).

Joining an unlocked session requires its ID, not proof of the content key. Guest Control frames with target 0 are forwarded unchanged. They are unencrypted, and the host uses `parse_json::<Control>()?`; invalid JSON or an unknown variant propagates out of `run()`. The orderly document flush and explicit close below the loop are skipped. Valid forged membership messages are also forwarded into handlers intended for relay-generated notices.

Reject guest-originated relay control notices, preserve trustworthy message provenance, and handle malformed guest requests without ending the agent. Verify that invalid/forged control messages leave the host and pending edits intact.

**R04 — P1: kick removes the membership record but does not revoke the connection. Source trace.**

[Kick implementation](D:/ajar/ajar/crates/ajar-relay/src/ws.rs:384), [routing loop](D:/ajar/ajar/crates/ajar-relay/src/ws.rs:178).

`kick()` sends a polite `Closed` notice and calls `drop_guest()`. The socket handler keeps its own sender and authenticated `me`, and continues forwarding incoming frames without checking membership. A client that ignores the notice can keep sending valid encrypted PTY or document input. Removing the outbox from the registry stops future broadcasts to it; it does not revoke its input authority.

Cancel/close the socket at the server and gate routing on live membership. Test continued input on the same socket after kick. Whether a previously invited person may rejoin with the same link is a separate product decision.

**R05 — P1: a guest reconnect can permanently detach its open document. Source trace.**

[Browser reconnect welcome](D:/ajar/ajar/web/src/main.ts:375), [document reader removal](D:/ajar/ajar/crates/ajar/src/docs.rs:167), [new guest initialization](D:/ajar/ajar/crates/ajar/src/main.rs:1013).

When the only reader disconnects, the host flushes and drops that document. The browser keeps its old `DocSession` and ID. A new welcome only updates identity/presence; it neither reopens the file nor performs document state exchange. Subsequent typing is sent to a document ID the host no longer has. The editor can look normal while its updates are rejected and never saved.

Reopen and resynchronize every active document after reconnect, with a strategy for local edits made while offline. Test a socket interruption while the sole guest edits a file, followed by more typing and an on-disk assertion.

**R06 — P1: remote pad edits leave the runtime stale and can be overwritten by a later command. Reproduced.**

[Refresh skips live documents](D:/ajar/ajar/pad/src/app.ts:186), [remote document updates](D:/ajar/ajar/pad/src/app.ts:291), [command publication](D:/ajar/ajar/pad/src/app.ts:680).

Remote Yjs updates change the live document but do not update the runtime. The subsequent store refresh skips any path with a live document, including the runtime write, but still advances `known` to the new server text. A typed shell command therefore reads the old file. Its later diff sees that old runtime content as a new local change and writes it over the remote user's saved text—even if the command itself only read files.

Use one explicit reconciliation mechanism to bring documents, models and runtime into agreement before commands and before diffing. Preserve remote changes received during commands rather than implicitly converting stale state into a local write. The reproduction uses a real Yjs update and the actual `refresh()`/`publish()` methods.

**R07 — P1: remotely deleted pad files are resurrected. Reproduced.**

[Remote deletions](D:/ajar/ajar/pad/src/app.ts:191).

Refresh disposes/removes an editor model but leaves the file in the runtime and leaves its live document registered. It also removes the path from `known`. The next publish sees a file that the server supposedly lacks and uploads it as newly created. A deletion in one browser can therefore be reversed by another browser's next command.

Apply deletions consistently to the runtime, model, document, stream mapping and selection. The focused reproduction shows a remote deletion followed by a PUT recreating the old file.

**R08 — P1: overlapping autosaves can commit older text last. Reproduced.**

[Autosave](D:/ajar/ajar/pad/src/app.ts:463).

`saveEdits()` clears `dirty` and starts an HTTP request without serializing it with earlier saves. If the user types again while that request is in flight, a second request starts. Network delivery/handling can commit the newer request first and the older request last. The older completion also replaces local `known` and runtime text. There is no remaining dirty entry to repair it, while the editor still shows the newer text and the status says saved.

Serialize each tab's writes, or add server-checked revisions and retry conflicts. Include command publication in that ordering. The reproduction deliberately completes two actual autosave requests in reverse order and confirms stale durable content.

**R09 — P1: an open agent document can truncate a file that later grows beyond 1 MB. Source trace.**

[Reconciliation](D:/ajar/ajar/crates/ajar/src/main.rs:973), [initial size refusal](D:/ajar/ajar/crates/ajar/src/main.rs:748), [last-reader close](D:/ajar/ajar/crates/ajar/src/docs.rs:167).

Initial document opening rejects a truncated read. Later `reconcile_docs()` only checks `binary: false` and ignores `truncated`. If a terminal replaces an open file with a larger one, its first 1 MB becomes the live document. Closing the last reader writes the document back, discarding the rest of the real file—even without another edit.

Apply editability checks on every reconciliation. When an open file becomes oversized or binary, detach or make it read-only without writing its old/partial content back. Test file growth after opening, followed by close.

**R10 — P1: durable pad creation has no service-wide or per-caller storage budget. Source trace.**

[Public PUT endpoint](D:/ajar/ajar/crates/ajar-relay/src/main.rs:217), [per-pad limits](D:/ajar/ajar/crates/ajar-relay/src/pad.rs:288).

The WebSocket quota is not used by the HTTP pad API. An anonymous caller can create unlimited valid names and fill each within the per-pad cap. Empty writes also create durable names, and expiry leaves permanent tombstones. The lease does not bound creation rate, total disk usage or inode growth. Filling the disk can break saves for all pads served by this relay.

Add HTTP creation/write rate limits, a global storage/inode budget, and explicit behavior when capacity is exhausted. Accounts are not required to implement these protections. No disk-exhaustion test was performed.

**R11 — P1: the advertised Docker image has both build and startup blockers. Source trace.**

[Docker build stage](D:/ajar/ajar/Dockerfile:16), [compiled script dependency](D:/ajar/ajar/crates/ajar-relay/src/main.rs:243), [runtime user](D:/ajar/ajar/Dockerfile:26).

The build stage copies `install.sh` but not `run.sh`, although the relay compiles `run.sh` with `include_str!`. The image therefore cannot build from this Dockerfile as written. After that is repaired, the non-root runtime user starts in the base image's root working directory, and the new default `--pad-dir ./ajar-pads` requires creating a directory there; no writable pad directory is prepared.

Copy every compile-time input and create an owned persistent data directory with an explicit `--pad-dir`. Verify a clean image build, startup health, pad write, and persistence across container replacement. Docker itself was not runnable here.

**R12 — P1: `--no-network` on Linux restricts TCP connect, not all outbound traffic. Source trace.**

[Network rule](D:/ajar/ajar/crates/ajar/src/sandbox.rs:516), [reported guarantee](D:/ajar/ajar/crates/ajar/src/sandbox.rs:391).

The only handled network action is `ConnectTcp`, while the UI says “no outbound network.” UDP operations are a distinct capability and are not covered by that rule. UDP/DNS traffic can remain possible. Implement the stated restriction or narrow the flag and warning to what is actually enforced. [Landlock network access rights](https://docs.kernel.org/userspace-api/landlock.html#network-flags).

The accompanying Linux check uses `/bin/sh` redirection to `/dev/tcp/…` and accepts any nonzero result. On systems whose `sh` does not support that extension, it succeeds as a test without attempting TCP at all; a network outage also passes. Use a known working client and controlled local listener, prove connectivity before confinement, and then prove denial. [Current network check](D:/ajar/ajar/scripts/linux-sandbox.sh:115).

**Further gaps to track**

These deserve follow-up but are not included in the numbered findings above:

- The sandbox grants whole `.cargo` and `.rustup` roots as writable “caches.” Those roots also contain credentials, configuration and executables. On Linux, granting `.cargo` grants its credential file too; toolchain replacement can affect later unsandboxed host commands. The existing decision to keep caches usable needs a more precise capability review than “cache” naming provides.
- Agent inbound/outbound and PTY channels are unbounded, while only relay outboxes are bounded. A slow connection or blocked host event loop can accumulate memory. The queue policy should cover the complete path.
- `Workspace::try_read()` rejects directories rather than requiring a regular file; opening a FIFO can block the host event loop. The credential scanner likewise performs blocking reads without requiring regular files.
- Relay registry removal is check-then-remove in both peer cleanup and reaping. A concurrent join/resume between checking and removal can lose a live session. Make these transitions atomic with respect to their predicates.
- Session reconnection does not replay all host policy/storage state. In particular, a relay restart creates an unlocked registry entry even when the host UI still says locked; a stored snapshot is not automatically regenerated if the workspace stays unchanged.
- New empty pad files are not explicitly marked dirty, and Share only copies a link—it does not wait for pending writes. There is no unload recovery, durable local draft, or export path for unsaved work in the current App.
- Typed-command execution and Run use different busy-state handling. Refresh deferral checks `App.busy`, which typed console commands do not set; autosave can also write into the runtime while a command runs.
- Shell completion uses an appended sentinel on the same line. A trailing shell comment or a parse error can suppress it, leaving the command promise waiting. Run constructs a shell argument with JSON quoting, which does not escape shell substitutions in filenames.
- Durable JSON replacement is atomic at rename but not explicitly fsynced with its containing directory. Backup/restore, disk-pressure behavior, and crash durability need operational tests. Reads and sweeps also perform synchronous disk work inside async tasks.
- The nonce cache is duplicate suppression for the most recent 4,096 frames, not a monotonic anti-replay mechanism. Its acceptance of old ciphertext is explicit in the code/tests. Revisit that threat-model decision alongside R01 rather than presenting it as equivalent to a sequence-number replay window.
- `git stash create` does not anchor a long-lived ref, untracked pre-session files are not checkpointed, and the farewell “changed since” helper actually uses current Git status rather than a diff from the checkpoint. Recovery wording should state these limits accurately.
- The UI and source comments contain stale promises: some modules still describe a release with no editing/sandbox, while those features exist. The documented root credential CSV was absent from this checkout; the historic live SSH rules were not verified here. Do not treat those old infrastructure notes as current evidence.

**Intentional scope, not newly discovered defects**

The current design explicitly leaves out pad accounts/locks, encryption for pads, persistent empty folders, networking/package installation from the browser shell, publication during never-ending commands, and host application preview URLs. Hosted snapshots are read-only, size-limited and session-lived. CPU, memory and disk use by guest processes are not capped. These decisions can be reconsidered, but they should not be mixed with implementation defects that violate existing behavior.

The early printed link is already documented in `docs/open-points.md`; the code still prints `open` before registration completes. This is a known readiness gap rather than a new review discovery.

**Repair order**

1. Repair and adversarially test protocol direction, guest control-message provenance, server-side revocation, and Linux confinement (R01–R04, R12). Make the documented security claims match what the platform enforces.
2. Fix document reconnect/reconciliation and persistence acknowledgement in the agent (R05, R09, R18, R25). Add tests for disconnects during typing, bulk rewrites, file growth, and failed writes.
3. Introduce explicit serialization/reconciliation for pad saves and command execution (R06–R08, R13–R14, R26). Assert final content in both browsers, both runtime filesystems and the server, after deliberately reordering/delaying traffic.
4. Bound HTTP storage growth and align request limits (R10, R16); reject impossible filesystem shapes (R24).
5. Repair Docker/development/deployment asset paths and enforce their build/start checks in CI (R11, R22–R23, R27).
6. Repair smaller UI, warning and verification gaps, then run real Linux/macOS suites and two-person browser sessions with realistic latency. Network and crypto tests need positive controls proving that the intended operation actually happened before asserting it was blocked or hidden.

The strongest existing pieces are the explicit hosted-versus-peer routing model, separation of durable pads from ephemeral encrypted snapshots, path canonicalization, debounced document handling, and breadth of happy-path smoke coverage. The missing work is chiefly proving those properties survive failure and concurrency. Successful local builds are useful evidence, but the eight reproduced failures demonstrate why release readiness needs those behavioral checks too.
